# Walksnail Ascent: протокол AR

Источник: статический разбор Caddx PC Tool v2.0.40 (dnSpy) и захваты USB в `analyze/Walksnail/COM-dumps`.
Описано своими словами, код Caddx в репозиторий не копируется.

## Физический уровень

- Устройство: VID `1D76`, PID `0101`, класс CDC-ACM (`bInterfaceClass = 0x0A`), драйвер Windows не нужен.
- Порт: 115200 бод, 8 бит данных, 1 стоп-бит, без чётности (`SET LINE CODING 00 C2 01 00 00 00 08`).
- Эндпоинты: `0x01` OUT, `0x81` IN (bulk). В USBPcap большие передачи разрезаются на URB по 64 КиБ,
  при этом `usb.data_len` в первом показывает полный размер (1 МиБ).
- После `REBOOT` устройство переотключается и обычно получает новый номер: в дампе адрес 28 → 29 → 30.
  Порт нужно искать заново по VID:PID, ориентируясь на серийный номер, а не на `COMx`.

## Кадр

Заголовок 36 байт, `Pack = 1`, little-endian. Поля и порядок подтверждены структурой `ArProtocolHeader`
и одинаковы для запроса и ответа:

| Смещение | Поле | Тип | Значение |
|---|---|---|---|
| 0 | `magic` | u32 | `0x4152544F` («OTRA») |
| 4 | `version` | u16 | `0x0CDC` (3292) |
| 6 | `type` | u16 | 1 = запрос, 2 = ACK |
| 8 | `msgid` | u16 | 0 |
| 10 | `unused` | u16 | `0xABCD` в запросах, `0` в ответах устройства |
| 12 | `command` | u32 | см. таблицу команд |
| 16 | `format` | u16 | 2 = бинарный |
| 18 | `userid` | u16 | 0 в запросах, в ACK повторяется |
| 20 | `length` | u32 | длина payload |
| 24 | `seq` | u32 | номер запроса, в ACK повторяется |
| 28 | `retry` | u32 | счётчик повторов |
| 32 | `crc32` | u32 | CRC32 (см. ниже) |

## CRC32

Алгоритм в Caddx: `InitCrcTable()` с полиномом `0xEDB88320` (отражённый IEEE), затем `CrcCalc`:
инициализация `0xFFFFFFFF`, обход таблицы по заголовку (поле `crc32` обнулено), затем по payload
длиной `length`, в конце XOR `0xFFFFFFFF`. Это стандартный zlib CRC32 по байтам
`header[0..36]` (с нулевым `crc32`) + payload.

Проверка на дампе: все кадры с полными данными совпали — `0x3C`, `0x03` (REBOOT с payload
`clean`), `0x72`, `0x73`. Кадры `0x74` не проверяются: USBPcap записал их обрезанными
(`frame.cap_len = 65535` при размере 1 048 603 байта), данных в файле просто нет. Это
ограничение снапшота, а не протокола; при следующих захватах нужно увеличить буфер.

Отсюда правило реализации: CRC считается по заголовку с обнулённым полем `crc32` и по фактически
переданному payload длиной `length`.

## Команды

| Код | Имя | Назначение |
|---|---|---|
| `0x03` | REBOOT | перезагрузка, payload — режим (`clean`) |
| `0x3C` | FIND_DEVICE | запрос сведений об устройстве |
| `0x72` | REMOTE_UPGRADE | вход в режим обновления, payload `OK` |
| `0x73` | SENDFILE_START | начало передачи файла, payload `ArFileInfo` |
| `0x74` | SENDFILE_DATA | блок данных |
| `0x75` | SENDFILE_END | конец передачи |
| `0x76` | UPGRADE_STATUS | опрос состояния |
| `0x77` | SEND_TEXT | текстовая команда |
| `0x78/0x79/0x7A` | GET/SET/FACTRESET BB_FREQ_CONFIG | частотная конфигурация |

## Ответ FIND_DEVICE (payload 300 байт)

Порядок полей подтверждён структурой `ResDeviceInfo` и разбором `ParseDeviceInfo`:
`receiveMaxSize` (u32), `sdkversion` (32), `devicename` (64), `cputemp` (u32), `firmwareInfo` (64),
`serialNumber` (32), `hardwareVersion` (32), `status` (u32), `detail` (64). Строки — ASCII с нулевым
заполнением. Смещения считаются от начала payload: 0, 4, 36, 100, 104, 168, 200, 232, 236.

Пример с живого устройства: `device_name = Ascent_GT_pro`, `firmware = Ascent_G_Sky_16_5_9`,
`hardware = FPV-Ascent-Sky-486-V1.0-1.0`, `serial = 6209`, `cputemp = 42`, `receiveMaxSize = 1048576`,
`status = 0`, `detail = OK`. Поле `OK` лежит именно в `detail`, `status` при этом равен нулю.

## Структура `ArFileInfo` (payload `0x73`, 328 байт)

| Смещение | Поле | Размер |
|---|---|---|
| 0 | `MD5` (32 hex-символа, ASCII) | 64 |
| 64 | `length` (u32) | 4 |
| 68 | `saveAsFile` (u32, 1 = сохранить на устройстве) | 4 |
| 72 | `filePath` — путь на устройстве, `/tmp/pc/<имя>.img` | 128 |
| 200 | `fileDir` — путь на ПК | 128 |

## Передача файла

`0x74` содержит блок изображения: в дампе `length = 1048576`, а `usb.data_len` показывает
1 048 576, но фактически URB на проводе — 65 508 байт. ACK на `0x74`:

| Смещение | Поле |
|---|---|
| 0 | резерв |
| 8 | `Length` (u32) — подтверждённый размер блока |
| 12 | `Offset` (u32) — смещение в файле: `0x1000`, `0x2000`, … |
| 16 | `Status` (ASCII `OK`) |

ACK на `0x73` и `0x75`: `Status = OK` со смещения 4. ACK на `0x72`: `OK` со смещения 4.
ACK на `0x03` (`REBOOT`): 68 байт, `OK`.

## Состояния обновления (`0x76`)

Payload 72 байта: `Percent` (u32, 0–100), `Status` (u32). Наблюдённые значения: `Percent=38, Status=2`,
`79/2`, `100/3`.

`AscentUpgStep`: None → FindDevice_Normal → Reboot_Clean → RemoteUpgrade → SendFileStart →
SendFileData → SendFileEnd → UpgradeStatus → Reboot → FindDevice_Clean.

Статусы из статического анализа: 0 — проверка образа, 1 — старт, 2 — в процессе, 3 — готово,
4 — вход в clean, 5 — ошибка. Отрицательные коды: -1 нет SD, -2 нет ПК, -3 нет файла, -4 битый файл,
-5 не та плата, -6 версия слишком мала, -7 режим, -8 тип образа, -9 CRC, -10 max, -11 flash, -12 chip ID.

## Контейнер `.img`

Заголовок 20 байт: сигнатура `41 53 57 00` («ASW\0»), затем `u32` тип (4 — передатчик Sky,
5 — приёмник Gnd), затем `u32` major, `u32` minor, `u32` patch. Проверено на всех восьми
файлах: `16_5_9`, `17_5_8`, `18_21_10`, `19_2_14` для Sky и Gnd.

Дальше идёт таблица разделов: число записей, размер записи (`8`), записи по 8 байт с адресами
загрузки (`0x08000000`, `0x08010000`, …). Файл передаётся целиком, без изменений; размер
совпадает с `length` в `ArFileInfo` (для Sky 17_5_8 — 12 164 404 байта).

## Наблюдения по версиям Caddx

- v2.2.8 (логи с `PortSession`): сессия владения портом, повторная отправка кадров, задержка
  переподключения 11 500 мс, ожидание до 16 933 мс.
- v2.2.9 (`V2.2.9_C`): находит устройство, отвечает `Ascent_GT_pro / Sky 18_21_10 / V1.0-1.0`,
  затем пишет «设备识别失败» (не удалось распознать устройство). Обмен кадрами при этом идентичен
  2.2.8, значит отказ в проверке таблицы поддерживаемых устройств внутри версии, а не в протоколе.
  Также встречается «异常帧长度, 跳过1字节重新同步, length=1079918686» — разбор кадра по `length`
  без ограничения, нужна защита от таких значений.
- v2.0.40 и v2.0.56 работают без `PortSession`; после `REBOOT` бывают `OpenSerial Failed: port does not exist`
  и повторные попытки.
- v1.1.1: после прошивки `FindDevice_Normal timeout`, устройство вернулось уже с новой прошивкой.

## Что осталось выяснить

- Команды `0x77`–`0x7A` (частоты) и работа с приёмником `Gnd`.
